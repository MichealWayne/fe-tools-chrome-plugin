# 维护者发布流程

## 触发与产物

`.github/workflows/build-release.yml` 在 PR 目标为 `master` 以及推送到 `master` 时运行。
PR 合并会产生一次 master 推送；直接推送也会触发。若要限制只能通过 PR 更新 master，
需要维护者在 GitHub 配置分支保护，本工作流不修改仓库设置。

构建作业只有 `contents: read` 权限，依次执行：

```sh
pnpm install --frozen-lockfile
pnpm run check:version
pnpm run typecheck
pnpm run lint:check
pnpm run test:run
pnpm run build
pnpm run package:extension
```

Node.js 20、pnpm 9 与 `zip`/`unzip` 由 GitHub 的 Ubuntu 执行环境提供或配置。
本地打包也需安装 `zip`；打包测试需 `unzip`。不需要新增 npm 依赖或个人访问令牌。

脚本检查 package、源码 Manifest 和构建 Manifest 的版本，以及页面入口、后台导入、
内容脚本、HTML 资源和双语 locale 文件。打包只接受构建运行文件；隐藏文件被排除，
符号链接和意外的顶层文件会被拒绝。固定排序和文件时间使相同构建内容得到相同 ZIP。

输出到被 Git 忽略的 `release-artifacts/`：

- `fe-tools-chrome-extension.zip`：根目录直接包含 Manifest，可解压加载。
- `SHA256SUMS.txt`：上述 ZIP 的 SHA256。

每次构建将这两个文件保存为 Actions Artifact，保留 14 天。Artifact 名包含版本、run ID
与 attempt；发布作业使用构建返回的 Artifact ID，确保重跑失败作业时仍读取原构建产物。
Artifacts 供维护者排障；普通用户从正式 Releases 下载。

## 新版本与草稿

1. 在发布 PR 中同步修改 `package.json`、`public/manifest.json` 的版本，并更新
   `CHANGELOG.md`、两个 README 中的当前版本。版本采用三段数字，例如 `1.8.1`。
2. 合并到 `master`，等待完整构建通过。
3. 仅 master 推送进入草稿作业。它使用 GitHub 提供的 `GITHUB_TOKEN`，需要仓库允许
   `contents: write`。组织策略或标签规则限制可能导致失败，应检查作业日志。
4. 新版本创建绑定当前构建提交的 `v<version>` 标签与 Draft Release，上传两个附件。
   **草稿不会公开发布，也不会成为 Latest；标签本身会出现在仓库中。**
5. 维护者在 Releases 中下载草稿附件，按中英文安装指南验证，随后手动发布并按需要
   设为 Latest。删除 Release 草稿提醒文字后再发布；其他版本与来源信息保留。

此流程不会自动递增版本，也不会覆盖旧版本。同版本的普通合并仍能得到 Actions 构建产物，
但不会将既有草稿或正式包更新为新提交；要分发变更，应在新 PR 中提升版本。

草稿作业使用独立并发组、`cancel-in-progress: false` 与 `queue: max` 串行处理，避免后续
合并取消正在上传的发布作业。排队顺序按到达该作业的顺序，不保证等于提交顺序；因此一版
对应一个固定提交，不通过覆盖草稿“追赶”master。

## 重跑与冲突

| 情况                             | 行为与处理                                       |
| -------------------------------- | ------------------------------------------------ |
| 同版本已有正式 Release           | 跳过，不修改附件、标签或说明                     |
| 同版本已有包含两个附件的完整草稿 | 跳过，继续验证原草稿；新代码需要提升版本         |
| 同提交上传中断，草稿缺少附件     | 校验已有附件摘要，仅补传缺失附件                 |
| 部分草稿属于其他提交             | 失败；回到原运行重试，或提升版本重新发布         |
| 标签存在但没有 Release           | 仅当标签解析到本次提交时继续，否则失败           |
| 已有附件内容不同或上传状态异常   | 失败，不自动删除或替换；维护者检查后决定处理方式 |
| Artifact 已过 14 天保留期        | 在原提交的运行中重跑全部作业，重新构建并打包     |

可在 Actions 中使用 Re-run failed jobs 恢复上传阶段失败。若只留下标签而没有草稿，原提交
重跑可继续创建草稿。已发布包出问题时发布修订版本，避免移动标签或覆盖相同版本。

## 发布前手工验证

验证对象必须是草稿附件解压出的目录，而不只是工作区中的 `dist/`：

- ZIP 校验通过，Chrome 可以加载，显示正确版本且没有扩展错误。
- 主弹窗、中英文切换、Postman 基本请求可用。
- 普通网页的二维码、技术栈检测、整页截图和节点截图入口可用。
- 在原目录替换文件并重新加载后，重要配置与历史数据按预期保留。
- 确认用户会看到的安装说明、变更记录和两个附件完整，再手动发布。

此前代码审查中的应用问题不由发布自动化修复。自动检查通过不能替代真实扩展生命周期
验证；草稿阶段用于保留这一步。代码回退不保证数据格式兼容，重要数据应先备份。

最新版下载链接在首个包含固定文件名附件的正式 Release 发布后才可用。已有旧命名附件的
历史版本不会被自动补传；需要新版本正式发布后建立该下载入口。
